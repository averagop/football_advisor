# 生产落地全量闭环修复设计

## 1. 文档目的

本设计用于一次性治理当前项目反复出现“局部修复完成，但整体仍不能落地”的问题。

本轮不以“修完已知报错”为完成标准，而以建立可重复、可审计、不可绕过的生产门禁为目标。任何代码、脚本、文档或人工结论，只要缺少规定证据，都不得宣称完成、可部署或生产就绪。

本设计覆盖当前仓库中能够识别的全部落地风险类别。对于尚未出现的未知问题，通过统一不变量、失败分类、证据矩阵、全新库验收、历史库迁移验收、故障注入和重复运行验收进行兜底，不依赖人工记住每一种具体错误。

## 2. 最高原则

1. 中国竞彩足球是唯一主投注平台，五种玩法固定为 SPF、RQSPF、CRS、TTG、HAFU。
2. 任何外部赔率不得替代竞彩官方赔率。
3. LLM 只生成文字叙述，不生成、修改或补齐概率、赔率、比分和价值判断。
4. 任何数据不足、过期、冲突、未映射或未校准状态必须进入 No Bet，不得静默降级为可投注。
5. `core.*` 只接受标准系统实体，不接受供应商名称、供应商编号或临时占位实体。
6. DuckDB 与 ChromaDB 保持职责隔离。
7. 所有关键时间统一为 UTC；无时区时间必须在数据源边界显式解释，不能由通用工具猜测。
8. 所有生产结论必须由机器可读证据产生，禁止根据日志印象或行数主观判定。
9. 所有真实外部调用必须可超时、可取消、可缓存、可追踪，单个来源失败不得拖死整个流程。
10. 未通过完整验收矩阵时，只能报告未完成项，不得使用“基本完成”“应该可用”等模糊表述。
11. 任何候选数据在决定用途、权重、延期或弃用前必须先调研，形成完整报告并由用户审核决定。
12. AI无权自行永久排除数据、删除采集链路、停止调研或把临时经验值宣布为正式预测标准。
13. 本设计中的数据调研与用户审批规则是最高数据治理指令；其他章节与其冲突时，以该规则为准。

## 3. 完成状态分层

项目不再只使用单一“完成/未完成”描述，而是分为四层：

### 3.1 CODE_READY

表示代码质量满足发布前提：

- 所有生产代码有对应自动化测试。
- 全量测试无失败。
- 非故意隔离的测试不得跳过。
- 单元测试不得访问真实网络。
- 编译、格式差异检查、数据库迁移测试通过。
- 安全扫描和 CodeRabbit 审查没有未处置的高严重度问题。

### 3.2 DEPLOYMENT_READY

表示服务可在目标环境部署：

- 全新数据库可初始化。
- 历史数据库可无损迁移。
- 配置检查能准确区分必需、可选和敏感配置。
- OpenWebUI、FastAPI、DuckDB、ChromaDB、外部 LLM 和本地备用 LLM 的连接边界明确。
- 缺少可选外部配置时服务仍可启动，并明确报告受限能力。
- 缺少必需配置时启动失败且错误可操作。

### 3.3 MATCH_READY

表示某一场比赛具备生成有效诊断报告的条件：

- 标准比赛、联赛、主客队实体完整。
- 竞彩五玩法均有明确状态：`OPEN` 或 `NOT_ON_SALE`。
- `OPEN` 玩法有完整官方赔率。
- 关键球队数据、阵容伤停和新闻信号满足当前业务规定的新鲜度与证据要求。
- 所有组件记录真实来源、更新时间和失败原因。

### 3.4 BET_READY

表示某一场比赛允许输出投注建议：

- 已满足 MATCH_READY。
- 概率模型通过正式校准发布门禁。
- No Bet 没有任何阻断原因。
- 竞彩玩法存在可评估赔率。
- 价值差达到阈值且不存在高风险冲突。

`MATCH_READY` 不等于 `BET_READY`。当前模型未校准时，即使数据完整，也只能输出诊断报告并保持 No Bet。

## 4. 统一失败分类

所有组件和验收脚本必须使用以下错误类别，不允许把内部错误伪装成外部阻塞：

| 类别 | 定义 | 最终处理 |
| --- | --- | --- |
| `INTERNAL_DEFECT` | 代码异常、错误映射、错误SQL、状态矛盾、迁移失败、报告契约破坏 | `FAILED` |
| `DATA_INVARIANT_FAILED` | 标准实体污染、重复核心事实、时间穿越、来源越权、玩法状态与赔率矛盾 | `FAILED` |
| `CONFIG_BLOCKED` | 必需配置缺失或格式非法 | `EXTERNAL_BLOCKED` |
| `PROVIDER_BLOCKED` | 网络、订阅权限、接口限流、供应商无数据 | `EXTERNAL_BLOCKED` 或单组件降级 |
| `SAFE_DATA_GAP` | 已明确确认关键数据缺失、过期或玩法未开售，且 No Bet 生效 | `SAFE_DEGRADED` |
| `PERFORMANCE_FAILED` | 超过阶段、单场或整体验收时限 | `FAILED`，除非证据证明是外部阻塞 |
| `SECURITY_FAILED` | 密钥泄漏、SQL越权、SSRF、未授权管理接口、敏感日志 | `FAILED` |
| `VERIFICATION_INCOMPLETE` | 测试、审查、四场验收或证据文件未完成 | 不得产生就绪结论 |

## 5. 总体修复架构

保持现有业务架构，不引入新的业务框架：

```text
请求解析
-> 配置与运行环境预检
-> 目标比赛解析
-> provider 数据写入 staging
-> staging 去重与格式校验
-> provider 实体映射
-> 标准实体重合并到 core
-> 竞彩五玩法完整性校验
-> 关键组件同步与证据写入
-> DataReadinessGate
-> DuckDB / ChromaDB 分别查询
-> 特征构建与消费证据校验
-> 概率模型
-> 五玩法价值引擎
-> No Bet
-> LLM 三字段叙述
-> 确定性报告渲染
-> 日志、差异与验收证据
```

新增的治理能力只承担三类职责：

1. 标准实体和数据不变量验证。
2. 发布与生产验收证据聚合。
3. 失败分类和阶段时限控制。

不得复制现有同步、特征、概率或报告业务逻辑。

### 5.1 API与搜索引擎边界

数据发现和事实采集必须按类型路由：

| 数据类型 | 主事实来源 | 辅助来源 | 搜索引擎权限 |
| --- | --- | --- | --- |
| 竞彩五玩法状态与赔率 | SportteryOfficialWeb | 无替代来源 | 不得替代官方数据 |
| 赛程、比分、球队统计 | 结构化API、官方数据、本地可信历史数据 | 多源交叉校验 | 仅发现线索 |
| 阵容、伤停、停赛 | 结构化API、球队或赛事官方来源 | 新闻交叉验证 | 仅辅助证据 |
| 新闻、战术、发布会、舆情 | ChromaDB中已入库文本 | SearXNG、Serper等发现入口 | 负责发现，不直接成为事实 |
| 第三方赔率和市场数据 | 经批准的结构化赔率API | 多源交叉校验 | 不得进入竞彩官方主链 |

搜索数据必须经过以下步骤才能进入系统：

```text
搜索发现
-> URL与来源安全校验
-> 正文抓取
-> 清洗与内容去重
-> 相关性筛选和重排
-> ChromaDB入库
-> 结构化信号抽取
-> 来源、实体和时间校验
-> 按用户批准用途进入报告、风险或候选实验
```

未经此流程的搜索摘要、网页片段或LLM概括不得进入预测和正式报告。

### 5.2 强制预测流程

所有OpenWebUI、FastAPI、CLI、穿测和运维预测入口必须执行同一流程：

```text
1. 解析请求、比赛和玩法
2. 配置、权限、数据库和目标比赛预检
3. 加载用户批准的数据准入清单和模型版本
4. 同步竞彩官方五玩法
5. 同步已批准的结构化数据API
6. 搜索、抓取、清洗并入库已批准的文本数据
7. staging去重、格式和来源校验
8. provider实体映射
9. 标准实体重新合并到core
10. 竞彩五玩法状态与赔率完整性校验
11. DataReadinessGate组件就绪校验
12. 分别查询DuckDB与ChromaDB
13. 特征构建、血缘、默认值和准入状态校验
14. ProbabilityEngine按已批准模型版本计算概率
15. OddsValueEngine按竞彩五玩法计算价值
16. NoBetPolicy执行不可绕过门禁
17. LLM只生成三字段叙述
18. 代码确定性渲染报告
19. 写入预测日志、差异、耗时和验收证据
20. 通过OpenWebUI或调用入口返回结果
```

任何步骤失败都必须终止或按明确规则进入安全降级；不得跳步、换序、静默补值或让LLM接管缺失环节。

### 5.3 穿测协议与结果格式

每场强制执行：全新库fixture、历史库迁移fixture、live、30分钟内cache二次运行、对话叙述注入、新闻缺失、阵容缺失、单provider超时和LLM失败。

机器证据至少包含以下结构：

```json
{
  "schema_version": "1.0",
  "request_id": "<REQUEST_ID>",
  "code_commit": "<GIT_COMMIT>",
  "database_path": "<ABSOLUTE_PATH>",
  "mode": "fixture|live|cache|fault_injection",
  "match": {
    "match_id": "<MATCH_ID>",
    "home_team_id": "<SYSTEM_TEAM_ID>",
    "away_team_id": "<SYSTEM_TEAM_ID>"
  },
  "readiness": {
    "code_ready": false,
    "deployment_ready": false,
    "match_ready": false,
    "bet_ready": false
  },
  "sporttery": {
    "SPF": {"status": "OPEN|NOT_ON_SALE", "odds_complete": true},
    "RQSPF": {"status": "OPEN|NOT_ON_SALE", "odds_complete": true},
    "CRS": {"status": "OPEN|NOT_ON_SALE", "odds_complete": true},
    "TTG": {"status": "OPEN|NOT_ON_SALE", "odds_complete": true},
    "HAFU": {"status": "OPEN|NOT_ON_SALE", "odds_complete": true}
  },
  "data_components": {},
  "feature_lineage": {},
  "model": {
    "version": "<MODEL_VERSION>",
    "calibrated": false,
    "approved": false,
    "probabilities": {}
  },
  "policy": {"recommendation": "NO_BET|BET", "reasons": []},
  "report": {"provider": "<PROVIDER>", "narrative_valid": true},
  "execution": {
    "verification_status": "COMPLETE|INCOMPLETE",
    "final_status": "<STATUS_OR_NULL>",
    "missing_evidence": [],
    "stages": [],
    "failures": []
  }
}
```

`final_status`只能是`PRODUCTION_READY`、`SAFE_DEGRADED`、`EXTERNAL_BLOCKED`或`FAILED`。缺少规定字段、必测场景或当次证据时，`verification_status`必须为`INCOMPLETE`，`final_status`必须为`null`，并在`missing_evidence`逐项列出缺口；此时不得输出任何生产就绪结论。只有`verification_status=COMPLETE`时才允许产生四种最终状态。

## 6. 全量风险与强制修复规范

### 6.1 需求和文档漂移

风险：文档宣称完成，但代码或数据库证据不支持；旧文档继续误导后续执行。

强制规范：

- `PROJECT_REQUIREMENTS.md` 只记录稳定产品要求。
- `ARCHITECTURE.md` 只记录已实现架构和明确边界。
- `PROGRESS.md` 每次改动记录真实测试结果、失败项、限制和下一步。
- 验收结果不得直接从 `PROGRESS.md` 读取，必须重新执行命令。
- 文档中的测试数量必须来自当次测试输出。
- 发现旧结论错误时必须追加更正，不能继续引用错误结论。

验收证据：需求不变量测试、文档状态检查、当次测试输出。

### 6.2 配置和敏感信息

风险：缺少配置时静默跳过；错误数据库路径；真实密钥进入仓库或日志；开发环境和生产环境行为不一致。

强制规范：

- 建立配置预检，输出每项配置的 `configured/missing/invalid/optional`，不得输出真实值。
- 数据库路径必须在启动证据中记录绝对路径。
- 验收脚本必须显式传入数据库路径，不能被 `.env` 静默覆盖。
- 必需配置缺失时快速失败；可选配置缺失时记录能力降级。
- 测试只使用 fake 值和 mock provider。
- 日志、异常和报告不得包含密钥、Cookie、完整连接串或授权头。

验收证据：缺配置、非法配置、路径覆盖、脱敏输出测试。

### 6.3 数据库初始化和迁移

风险：只支持新库；历史库升级失败；视图先于字段创建；迁移部分成功导致脏状态。

强制规范：

- 全新空库初始化必须一次成功。
- 至少使用一份历史结构副本验证升级。
- 所有迁移在事务或可恢复步骤中执行。
- 迁移必须幂等，连续执行两次结果一致。
- 字段、表、索引和视图依赖顺序必须由测试覆盖。
- 迁移失败不得继续启动预测服务。

验收证据：新库初始化测试、历史库迁移测试、二次迁移测试、失败回滚测试。

### 6.4 标准实体映射

风险：供应商名称或编号写入核心表；数字编号与名称别名互相删除；映射晚于赛程写入；已有比赛映射绕过球队一致性检查。

强制规范：

- `core.fact_match_schedule.home_team_id/away_team_id` 必须存在于 `core.dim_team_mapping.system_team_id`。
- `core.*` 禁止写入中文队名、供应商编号、`TEAM_*` 临时值或 `M_ST_*` 临时比赛。
- 一个供应商球队允许多个合法别名映射到同一标准球队。
- 映射修正与别名新增必须使用不同语义，不能依靠“同名即删除”猜测。
- 已存在比赛映射时仍须验证 staging 主客队映射与核心赛程一致。
- 映射更新后必须对本次目标比赛重新合并核心赛程。
- 映射失败必须保留在 staging 并报告，不得回退写入 core。

验收证据：数字编号与中文别名共存测试、映射顺序测试、已有比赛映射一致性测试、核心实体污染查询必须为零。

### 6.5 Staging 去重和核心幂等

风险：每次快照重复写入相同赛程；重对账逐条重复处理；数据量和耗时持续膨胀。

强制规范：

- 赛程 staging 以 `(source_provider, provider_match_id, match_time)` 为业务唯一键。
- 同一快照重复写入必须更新或忽略，不能新增重复赛程。
- 赔率快照允许按真实快照时间保留历史，但同一业务主键必须幂等。
- 重对账必须先提取唯一目标比赛，再解析和重合并。
- 同步一次和同步十次后的核心赛程行数必须一致。
- 对既有重复数据提供安全清理或迁移步骤，并先在副本验证。

验收证据：重复同步测试、重复快照测试、历史重复数据迁移测试、行数稳定性测试。

### 6.6 竞彩五玩法

风险：只检查五个状态行，不检查开放玩法赔率；第三方赔率替代未开售玩法；状态和赔率互相矛盾。

强制规范：

- 每场必须有 SPF、RQSPF、CRS、TTG、HAFU 五种最新状态。
- `OPEN` 的 SPF/RQSPF 必须存在官方三路赔率。
- `OPEN` 的 CRS/TTG/HAFU 必须存在对应官方明细赔率。
- `NOT_ON_SALE` 必须保留未开售语义，不允许第三方赔率替代。
- 竞彩主链只读取 `SportteryOfficialWeb`。
- 缺状态、开放但无赔率、赔率存在但状态未开售均属于数据不变量失败。
- RQSPF 必须同时具备让球数和三路赔率。

验收证据：五玩法状态矩阵、开放玩法赔率计数、来源隔离测试、未开售替代测试。

### 6.7 时间、时区和新鲜度

风险：本地时间被当作UTC；数据时间在未来；使用写入时间代替来源时间；旧数据被新ETL时间伪装为新数据。

强制规范：

- 外部数据适配器负责把源时间转换为带时区UTC。
- 通用 `as_utc` 不再猜测无时区时间的来源时区。
- 数据库中的无时区 `TIMESTAMP` 必须统一约定为UTC并只写入转换后的UTC值。
- 新鲜度优先使用 `source_updated_at/snapshot_time`，不得使用 ETL 写入时间伪装来源新鲜度。
- 未来时间超过允许钟差必须失败。
- 30分钟门禁按组件分别计算，不以单一总时间覆盖组件缺失。
- 所有报告显示UTC时间并可附用户时区展示，但内部计算只用UTC。

验收证据：北京时区输入、UTC输入、夏令时、未来时间、旧来源新写入等测试。

### 6.8 同步、缓存和失败抑制

风险：状态写成功但数据不可消费；失败缓存阻止恢复；同一组件重复调用；外部来源无限重试。

强制规范：

- 同步成功必须基于实际数据证据，不基于 provider 返回字符串。
- 球队统计成功必须精确匹配赛程主客队标准实体。
- 阵容、伤停、新闻分别记录独立真实更新时间。
- 30分钟内成功缓存可复用；失败缓存必须记录原因和可重试时间。
- 单次预测内同一组件最多调用一次。
- 每个 provider 有独立超时，总同步有整体截止时间。
- 超时后任务必须可取消，不能留下后台线程继续写库。
- 可选来源失败不覆盖关键来源状态。

验收证据：缓存命中、缓存过期、失败恢复、重复调用、单源超时、整体超时测试。

### 6.9 数据就绪状态

风险：同步层显示成功，DataReadinessGate显示缺失；多个层级结论矛盾。

强制规范：

- 同步证据和 DataReadinessGate 使用同一组组件定义和标准实体。
- 每个组件输出：状态、来源、行数、来源更新时间、年龄、实体匹配结果、错误类别。
- 就绪状态必须可从数据库重新计算，不能只相信进程内结果。
- `ready=true` 只有全部关键组件通过时成立。
- 可选组件缺失只能进入风险说明，不能伪装为关键组件失败。

验收证据：同步结果与重新加载状态一致性测试、实体错配测试、组件缺失测试。

### 6.10 采集到消费的数据血缘

风险：数据库有数据，但宽表、特征或模型没有使用；只按行数宣称采集成功。

强制规范：

- 每个预测特征记录来源表、来源实体、来源时间和是否使用默认值。
- 关键球队特征使用默认值时必须设置明确质量标志。
- 验收必须比较输入球队差异；不同球队全部退化为相同默认特征时失败。
- 已采集但未消费的数据必须进入候选数据登记，不得由AI直接归类为无价值或永久不使用。
- 候选数据在完成调研和用户审批前统一标记为“待调研/待决定”，不得计入已批准的生产特征覆盖率。
- 宽表必须暴露主客队统计命中状态和默认值原因。

验收证据：四场特征血缘、默认值检测、已采集未消费清单、宽表与底表对账。

### 6.10A 候选数据调研与用户审批

风险：AI凭经验决定数据无用；未经实验永久排除数据；只展示推荐结论而不展示反方证据；权重和阈值长期停留在拍脑袋状态。

强制规范：

- 所有现有和未来数据建立候选登记，记录定义、来源、当前采集状态、当前消费状态和负责人。
- 候选登记必须使用固定字段：`data_id`、`name`、`definition`、`sources`、`collection_status`、`current_usage`、`research_status`、`research_report_path`、`evidence_level`、`leakage_risk`、`proposed_role`、`proposed_weight_range`、`user_decision`、`decision_time`、`approved_model_versions`、`owner`和`last_reviewed_at`。字段缺失时不得进入审批。
- 每项候选数据必须形成独立调研报告，至少包含：影响机制、可用API与官方来源、搜索引擎角色、许可与成本、覆盖率、缺失率、时效性、实体映射率、异常与操纵风险、未来穿越风险、与现有特征相关性、单特征实验、组合实验、消融实验、时间外回测、校准影响、分赛事稳定性、故障影响、推荐用途、候选权重范围、使用风险和不使用损失。
- 报告必须同时展示支持进入和反对进入的证据，并标注证据不足部分。
- 调研报告必须先提交用户审核。用户未作决定时，状态只能保持“报告待审核”，AI不得替用户选择。
- 用户可批准进入正式概率、No Bet或风险、报告上下文、离线校准，也可决定延期或弃用。
- 只有用户明确决定弃用后，才允许停止后续接入；是否删除既有采集链路仍需单独确认。
- 已由项目需求明确批准的产品硬规则和安全规则不重复执行候选审批；任何数据特征、模型权重、数据源权重、经验阈值和数据用途均不得借“产品规则”名义绕过调研。
- 发现新数据类型时，必须先进入登记和调研流程，不得直接塞入模型，也不得直接排除。

首批强制调研清单：Elo与动态Elo、近期战绩、进失球、xG与射门质量、主客场与中立场、阵容与阵型、伤停停赛与球员重要性、休息与旅行、H2H、积分榜和赛事动机、天气场地海拔、裁判、新闻发布会战术舆情、竞彩赔率变化、第三方赔率、资金流、球员名单与俱乐部表现、教练变化、历史事件滚动指标。

验收证据：候选数据登记表、逐项调研报告、用户审批记录、准入清单版本和弃用决定记录。

### 6.11 概率模型和校准

风险：未校准模型被当成可投注模型；默认特征生成看似精确的概率；模型升级没有版本证据。

强制规范：

- 模型必须携带版本、参数版本、校准状态和训练截止时间。
- 未校准时允许显示诊断概率，但强制 No Bet。
- 关键特征缺失时报告必须明确概率为诊断值。
- 模型发布必须通过样本量、Brier Score、LogLoss、基线改进和时间外验证门禁。
- 回测严格使用赛前可见数据。
- 模型参数变更必须有独立评估报告，不能在修复数据链路时顺便调参。
- 当前泊松权重0.72、Elo权重0.28、状态修正0.018及上限0.035、Elo尺度400、主场Elo加成65、半场45%/55%、价值阈值5%和市场偏差阈值15%均标记为待调研基线，不得描述为正式标准。
- 权重确定必须经过：质量审计、防穿越检查、无特征基线、单特征实验、组合实验、消融实验、时间外滚动回测、校准、分赛事稳定性、成本故障评估、用户审批和模型版本固化。
- 每个权重和阈值必须记录依据类型：产品硬规则、外部研究证据、本项目实证、安全阈值或临时经验值。
- 临时经验值可以用于诊断实验，但不得使模型进入BET_READY。

验收证据：未校准禁投测试、默认特征风险测试、时间穿越测试、模型版本日志测试。

### 6.12 赔率价值和 No Bet

风险：禁投报告仍突出 `value=True`；未开售玩法进入价值评估；不同玩法概率映射错误。

强制规范：

- 五玩法分别使用对应概率分布和官方赔率结构。
- 未开售或赔率不完整的玩法不得执行价值判断。
- No Bet 发生时，报告可显示诊断性市场偏差，但不得标记为可投注价值项。
- No Bet 原因必须中文化、去重并按严重度排序。
- 高风险、未校准、关键数据缺失、来源越权、时间异常任一成立即阻断投注。
- 禁投不影响保存模型诊断结果，但利润字段必须为空。

验收证据：五玩法价值测试、未开售测试、禁投报告测试、利润语义测试。

### 6.13 LLM和报告

风险：硬编码无证据战术结论；LLM编造数字；验证器误报；模型失败后报告结构丢失。

强制规范：

- LLM 只返回 `key_factors/main_risks/reasoning_summary` 三字段。
- 提示词只提供已验证的结构化摘要和允许引用的文本证据。
- 叙述不得包含新数字、未知球队、无来源伤停或确定性收益措辞。
- No Bet 校验必须按完整语义匹配，不能把“不建议投注”误判为建议投注。
- 实时验收必须支持外部叙述文件或对话注入，禁止默认硬编码战术事实。
- 外部 LLM 失败后按外部模型、本地备用模型、纯代码模板顺序回退。
- 无论LLM是否成功，结构化事实章节必须完整。
- 所有用户可见标题、风险原因、状态和说明必须为中文；供应商名、代码和玩法缩写除外。

验收证据：三字段契约、幻觉数字、未知实体、否定语义、三级回退、中文输出测试。

### 6.14 API与OpenWebUI

风险：开发脚本能运行但正式入口不能；管理接口无授权；错误响应不明确；OpenWebUI绕过固定流程。

强制规范：

- 正式预测只通过 FastAPI `PredictionPipeline`。
- OpenWebUI 工具不得直接查询数据库或调用概率引擎子步骤。
- 请求必须校验比赛、玩法和参数。
- 管理与同步接口需要管理令牌，令牌日志必须脱敏。
- HTTP 状态码和错误体必须保留统一失败类别及可操作说明。
- 同一请求ID贯穿同步、特征、模型、报告和日志。
- API启动健康检查分别报告服务、DuckDB、ChromaDB和可选外部组件状态。

验收证据：正式入口集成测试、鉴权测试、非法输入测试、请求ID测试、受限健康状态测试。

### 6.15 SQL与安全边界

风险：SQL注入、多语句、非SELECT访问、SSRF、敏感数据外发。

强制规范：

- 查询工具只允许单条SELECT并强制LIMIT。
- 所有动态值参数化。
- URL抓取执行协议、主机、重定向和内网地址限制。
- 外部LLM和搜索请求只发送完成任务所需的最小文本。
- 不向第三方发送密钥、数据库路径、完整环境变量或无关私有数据。
- 日志和异常统一脱敏。

验收证据：SQL注入、多语句、SSRF、重定向、脱敏测试和安全扫描。

### 6.16 性能、并发和资源上限

风险：四场串行执行数十分钟；线程超时后继续运行；数据库锁冲突；重复数据放大耗时。

强制规范：

- 每个provider、每个组件、每场比赛和整套验收均有独立截止时间。
- 验收输出阶段进度，不允许长时间无输出。
- 并发写DuckDB必须经过现有串行写入边界或明确锁策略。
- 缓存模式不得重新调用已成功且未过期的关键组件。
- 性能门禁以固定fixture和受控provider测试，不以不可控网络延迟作为唯一证据。
- 超时必须产生机器可读失败记录。

验收证据：受控慢provider、取消、数据库锁、四场fixture时限、缓存重复运行时限测试。

### 6.17 测试可信度

风险：单元测试访问真实网络；跳过测试被忽略；测试名和断言不一致；模拟数据掩盖实体错误。

强制规范：

- 单元测试默认禁网，任何网络访问均视为测试失败。
- 真实provider测试单独归为烟雾测试并显式执行。
- 每个缺陷先写失败测试并确认失败原因，再修改生产代码。
- 跳过测试必须带责任、原因和解除条件；发布门禁列出全部跳过项。
- 验收测试使用真实DuckDB schema和标准实体，不只使用mock行数。
- 测试名称必须对应实际断言。
- 全量测试结果必须记录总数、失败数、错误数和跳过数。

验收证据：禁网测试夹具、全量测试输出、跳过项清单、缺陷红绿记录。

### 6.18 可观测性和审计

风险：只能看到最终失败，不知道卡在哪一步；状态表和日志矛盾；无法复现某次报告。

强制规范：

- 每次预测生成唯一请求ID和预测ID。
- 每个阶段记录开始、结束、耗时、状态、来源和错误类别。
- 验收JSON保存配置摘要、数据库路径、代码提交、测试结果、四场结果和时间戳。
- 预测日志保存模型版本、特征质量、No Bet原因和报告生成来源。
- 证据文件不得包含敏感值。
- 验收失败必须能够定位到具体组件和不变量。

验收证据：请求链路测试、证据JSON模式测试、失败定位测试。

### 6.19 部署、恢复和回滚

风险：修复只在开发库有效；生产库不可恢复；迁移后发现问题无法回滚。

强制规范：

- 迁移前创建数据库副本并验证可读取。
- 所有数据修复先在副本运行并生成差异报告。
- 禁止对唯一生产库直接执行未验证清理。
- 应用启动前运行只读预检；预检失败不进入服务就绪状态。
- 回滚必须恢复代码版本和数据库副本，不能只回滚代码。
- 发布后执行固定四场只读验收。

验收证据：副本迁移、差异报告、失败恢复演练、发布后只读验收。

### 6.20 AI执行纪律

风险：AI只修最显眼问题；凭推断宣称完成；遗漏文档和测试；为了通过测试篡改断言。

强制规范：

- 每个任务必须包含目标、受影响文件、失败测试、最小实现、验证命令和证据。
- 未看到失败测试前不得修改对应生产行为。
- 不得删除、弱化或跳过失败测试来获得绿色结果。
- 不得使用临时脚本修改生产数据库作为正式修复。
- 不得根据历史测试结果宣称当前通过。
- 每完成一个阶段立即运行阶段测试，不把所有验证拖到最后。
- 遇到无法验证的外部依赖必须标记阻塞，不得构造成功数据。
- 发现新问题必须先归入本设计的风险类别；若无法归类，新增类别和门禁后再修复。
- 每次修改后更新 `PROGRESS.md`，明确完成、验证、限制和下一步。
- AI在提出“不进入预测”“仅作上下文”“停止采集”或“弃用”前，必须先完成调研报告并让用户审核。
- AI不得只给推荐结论，必须同时给出数据证据、反方证据、未确定项、实验限制和可能损失。
- 用户未明确批准时，AI不得修改正式准入清单、正式模型权重或数据弃用状态。

### 6.21 批次完成不可自证门禁

风险：AI把“我已经检查”“测试大体通过”“文档已更新”当成批次完成证明，导致未跟踪文件、未复审问题、证据缺口或历史失败继续留到后续批次。

强制规范：

- 每个批次必须生成 `docs/verification/batches/batch-N-evidence.json` 和 `docs/verification/batches/batch-N-review.md`。
- 批次证据必须符合 `docs/verification/templates/batch-evidence.schema.json` 的字段约束。
- 提交前必须运行 `.\.runtime\python\python.exe scripts\verify_batch_completion.py --batch N --mode pre-commit`。
- 提交后必须运行 `.\.runtime\python\python.exe scripts\verify_batch_completion.py --batch N --mode post-commit`。
- `blocking_gaps` 非空、CodeRabbit未成功执行、命令存在非零退出码、必要证据文件缺失或提交后工作区不干净时，该批次只能标记为“未通过”，不得进入下一批。
- AI总结、`PROGRESS.md`、CodeRabbit单次输出、人工口头判断都不能单独证明批次完成；只能作为 evidence JSON 的输入证据。
- 未跟踪临时文件、未提交验收文件和未解释改动在 post-commit 模式下均为阻断项。
- 若批次被判定未通过，最终回复必须明确写出“批次N未通过”、阻断项和下一步修复范围。

5. 对话叙述注入后继续报告和日志流程。
6. 故障注入：新闻缺失、阵容缺失、一个provider超时、LLM失败。

退出条件：所有内部不变量通过；外部缺失准确归类；No Bet不被绕过；证据JSON完整。

## 9. 不在本轮伪造完成的事项

以下事项需要真实外部条件或历史样本，本轮只能实现代码和门禁，不能伪造业务就绪：

- 新闻搜索服务的真实可用性。
- 阵容和伤停供应商的真实覆盖率。
- 外部LLM和本地Qwen的部署可用性。
- 足够历史样本上的模型校准结果。
- 真实交易所资金流。
- 外部provider订阅权限和限流状态。

这些条件缺失时，服务可以达到 `CODE_READY` 和 `DEPLOYMENT_READY`，目标比赛必须准确进入 `SAFE_DEGRADED/No Bet`，不能宣称 `BET_READY`。

## 10. 预期最终结果

完成本设计后，项目应具备以下特征：

1. 已知问题不会再因不同检查层标准不一致而分批暴露。
2. 新问题会被统一不变量和发布门禁阻止，而不是进入正式报告。
3. 外部数据缺失不会被误认为代码缺陷，也不会被伪装成成功。
4. 每次发布都能从全新库和历史库重复验证。
5. 四场目标比赛可以稳定走完固定流程；数据不够时明确No Bet，数据充分且模型校准后才允许投注建议。
6. AI或人工都不能绕过测试、证据、文档和验收矩阵直接宣布完成。
