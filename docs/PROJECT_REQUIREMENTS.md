# 竞彩足球辅助决策系统需求

## 项目定位

本项目是一个足球赛事赛前分析与竞彩足球辅助决策系统。系统通过 OpenWebUI 提供自然语言交互，输出标准化赛事预测分析报告。

系统目标不是完美预测比赛结果，也不是自动下注或承诺收益，而是提供：

- 赛前数据整合
- 概率预测
- 赔率价值识别
- No Bet 风险拦截
- 可追溯的标准化分析报告

## 前端与模型要求

- OpenWebUI 是唯一前端入口。
- Codex、Antigravity、Trae、豆包等对话/IDE 工具可以作为开发、运维、手动同步或调试入口，但必须通过同一套 FastAPI、CLI 或 MCP/OpenAPI 工具调用后台能力，不得绕过后台流程直接生成正式分析。
- 本地部署 Ollama + Qwen2.5-7B。
- 外部 OpenAI-compatible LLM API 是可选增强项，不是本地最小闭环的强依赖。
- 在未配置外部 OpenAI-compatible LLM API 时，本地 Qwen2.5-7B 可作为自动报告生成引擎。
- 在配置外部 OpenAI-compatible LLM API 时，外部 LLM 优先用于报告生成，本地 Qwen2.5-7B 作为 Backup Engine。
- 本地 Qwen2.5-7B 不作为主预测模型，不直接参与概率计算。
- Codex 不作为生产运行时 LLM 接口；Codex 只用于开发、调试、手动高级分析、数据同步和运维操作，不作为 OpenWebUI 自动预测链路中的模型依赖。

## 数据架构

系统采用双库分离：

- DuckDB：结构化数据，包括赛程、历史交锋、球队战绩、赔率、伤病、天气、球员数据等。
- ChromaDB：非结构化文本，包括球队新闻、赛前言论、战术解读、舆情内容等。

强制工具拆分：

- `query_match_stats`：只访问 DuckDB，只查结构化统计数据。
- `search_team_news`：只访问 ChromaDB，只查新闻舆情文本。

数据同步要求：

- 支持日常定时基础数据同步。
- 支持预测前按需实时同步。
- 同步与查询必须解耦。
- 预测流程必须先同步，再查询。
- 预测所用关键数据更新时间不得超过 30 分钟。
- 所有异常必须明确报错，不允许静默失败。
- 免费搜索可以作为新闻、战术、舆情和公开网页发现的优先补充来源；赔率、赛程、比分、伤停等关键结构化数据在搜索结果不足、无法校验或过期时，必须调用已配置 API、使用可信结构化源，或进入 No Bet/数据不足状态。
- 成本优先级必须遵循物美价廉原则：先用本地缓存和本地历史数据，再用免费结构化源，再用免费搜索发现文本线索，最后才调用低成本付费 API 或外部 LLM。
- 数据源必须按类型路由：
  - 赛程、比分、赔率、伤停、阵容、球队统计等关键结构化数据优先走 DuckDB 缓存、免费结构化源、低成本结构化 API，不得以搜索结果作为唯一事实来源。
  - 面向实际购买竞彩足球时，竞彩足球固定奖金/赔率必须优先采用中国竞彩网官方公开信息；The Odds、RapidAPI 等国际或第三方赔率源只能作为交叉校验或补充来源，不能替代官方竞彩赔率。
  - 新闻、战术、舆情、发布会文本优先走 ChromaDB 缓存、SearXNG、Google Programmable Search JSON API，再进入抓取、清洗、去重和 embedding 入库。
- 付费 API 和外部 LLM 必须按需调用，并缓存短时间内相同比赛和相同搜索结果，避免重复消费。

## 数据调研与用户决策最高规则

本节是所有数据采集、特征工程、模型权重、预测流程和后续开发的最高业务规则。任何后续设计、代码、脚本或AI建议与本节冲突时，以本节为准。

已经在本文件中明确批准的产品硬规则和安全规则，包括竞彩主体地位、五种玩法、30分钟关键数据新鲜度、LLM不得生成概率、SELECT-only SQL和No Bet安全边界，无需重复走候选数据审批；但任何数据特征是否进入模型、如何使用、赋予何种权重，以及任何经验阈值是否升级为正式预测标准，仍必须执行本节规定的调研和用户审批。

- 任何可能影响预测、风险判断、No Bet、报告解释或模型校准的数据，在决定“不进入预测”“只作上下文”“停止采集”或“永久弃用”前，必须先完成专项调研。
- 调研必须覆盖数据定义、影响机制、可用来源、API与搜索能力、覆盖率、缺失率、时效性、实体映射、未来数据穿越、异常风险、成本、延迟、相关性、增量预测价值、消融结果、时间外回测和分赛事稳定性。
- 调研结果必须先形成用户可审阅报告，明确列出支持使用、限制使用和不使用的证据，不得只给结论。
- 用户拥有数据最终决策权。只有用户明确批准后，数据才可进入正式概率模型、No Bet、风险等级、报告上下文或离线校准；只有用户明确决定后，数据才可延期或弃用。
- AI、代码实现者和自动化流程无权自行永久排除、删除采集链路、停止调研或宣布数据无价值。证据不足时只能标记为“未调研”“调研中”或“报告待审核”。
- 当前已存在但未经专项调研批准的模型参数和增强特征，只能作为未校准诊断基线，必须强制 No Bet，不得描述为正式预测标准。
- 每一次权重、阈值、特征用途或数据源优先级变更，都必须记录依据类型：产品硬规则、外部研究证据、本项目实证结果、安全阈值或临时经验值。
- 临时经验值不得使模型进入可投注状态；在完成调研、回测、校准和用户批准前，`BET_READY` 必须为假。

候选数据状态固定为：

```text
未调研
-> 调研中
-> 调研报告待审核
-> 用户批准进入正式概率模型
   / 用户批准仅用于No Bet或风险
   / 用户批准仅用于报告上下文
   / 用户批准仅用于离线训练与校准
   / 用户决定延期
   / 用户决定弃用
```

数据质量要求：

- 数据进入预测前必须经过规则硬校验，包括字段完整性、类型范围、时间新鲜度、未来数据穿越、实体映射、重复检测、来源可信度、多源一致性和异常波动检查。
- bge-m3 与 bge-reranker-v2-m3 可用于新闻、战术、舆情文本的相关性初筛、去噪和重排。
- 本地 Qwen2.5-7B 只能在外部 LLM 失败后作为报告生成备用，不参与新闻压缩、重排、概率计算或数据质量裁决。
- 外部 OpenAI-compatible LLM 可用于新闻文本的结构化信号抽取和解释，但抽取结果必须保留 `generated_by`、`source_text_hash`、`confidence` 和 `requires_cross_check` 等审计字段，不能直接覆盖事实数据。
- 最终数据质量门禁必须由规则、来源可信度、多源交叉校验、时间新鲜度和 No Bet policy 决定；LLM 不得绕过或降低 No Bet 门槛。

## 固定预测流程

```text
自然语言输入
-> 解析比赛与玩法
-> 配置、权限、数据库和目标比赛预检
-> 按用户已批准的数据准入清单同步最新数据
-> 结构化API数据写入 staging
-> 搜索引擎只发现新闻、战术和舆情线索
-> 网页安全检查、正文抓取、清洗、去重、相关性筛选和 ChromaDB 入库
-> staging 去重、格式校验和 provider 实体映射
-> 标准实体重新合并到 core
-> 竞彩五玩法状态与官方赔率完整性检查
-> DataReadinessGate 数据就绪检查
-> DuckDB 查询结构化数据
-> ChromaDB 检索新闻舆情
-> 特征工程、数据血缘和默认值检查
-> 概率模型计算胜平负/比分/大小球概率
-> 竞彩五玩法赔率隐含概率与价值判断
-> 风险评估与 No Bet 判断
-> LLM 只生成三字段叙述
-> 代码确定性生成标准报告
-> 写入预测日志、差异和机器可读验收证据
-> OpenWebUI 返回结果
```

所有正式入口、穿测脚本和运维工具必须保持上述顺序。任何步骤不得被LLM、脚本参数或人工临时逻辑绕过。

## 竞彩足球核心要求

- LLM 不能直接当预测引擎。
- 必须由独立概率模型输出胜平负、比分、大小球等概率。
- 必须对赔率隐含概率进行归一化，并与模型概率比较价值差。
- 必须支持 No Bet 机制。
- 必须支持严格时间顺序回测，防止未来数据穿越。
- 必须支持概率校准与指标评估。

## 报告必须包含

- 胜平负倾向
- 让球胜平负倾向
- 比分参考
- 大小球倾向
- 总进球参考
- 置信度
- 风险等级
- 是否建议投注
- 模型概率
- 赔率隐含概率
- 价值差
- 数据更新时间
- 历史交锋
- 近期状态
- 主客场表现
- 伤病
- 赔率变化
- 天气
- 新闻舆情
- 核心胜负手
- 主要风险点
- No Bet 原因
- 数据来源
- 推理链摘要

## 默认策略

- 当前概率模型采用可解释的待调研基线：Poisson 比分模型 + Elo/近期状态修正。现有权重属于临时经验值，不代表已经通过统计验证的正式预测标准。
- 未通过校准发布门禁时，模型版本必须标记为未校准，诊断概率可展示但不得输出可投注建议。
- 阵型、H2H、疲劳等增强特征在调研和用户审批完成前保持候选状态；临时可仅用于报告或风险，但不得被AI自行永久排除。
- 价值投注当前临时阈值为模型概率相对赔率隐含概率至少高出 5%；该值必须通过专项回测和用户审批后才能成为正式标准。
- 风险等级分为低、中、高。
- 高风险比赛即使存在模型倾向，也默认不输出强投注建议。
- 不输出“稳胆”“必胜”“稳赚”“稳赢”等确定性或收益承诺表述。

## 系统不变量规则（2026-06-13 闭环）

以下规则构成系统行为的最低保证，违反即视为缺陷：

### R1 - 竞彩赔率单一来源

竞彩五玩法（SPF/RQSPF/CRS/TTG/HAFU）的赔率仅使用 SportteryOfficialWeb provider。第三方赔率不得进入竞彩主链路。

### R2 - 预测语义分离

model_predicted_outcome（核验用）与 value_candidate_outcome（价值候选）分别存储，互不混淆。赛后核验使用前者。

### R3 - No Bet 语义

No Bet 策略明确的比赛，盈亏计算跳过，不产生虚构收益。日志中 profit_loss_unit 必须为 NULL。

### R4 - LLM 只写叙述

LLM 生成的报告仅包含文本叙述（key_factors、main_risks、reasoning_summary），不得包含数字。所有概率、赔率、比分由系统代码渲染。

### R5 - UTC 语义统一

所有时间以 UTC 为准，未来时间戳拒绝进入同步流程。

### R6 - 中立场主场优势清零

is_neutral_venue = TRUE 时，主场优势为 0.0。

### R7 - 组件证据就绪

阵容/伤停/新闻的 updated_at 必须由对应组件的真实写入时间证明，不得用其他字段兜底。

### R8 - 30分钟缓存与去重

同步组件在30分钟TTL内复用缓存结果；失败缓存抑制重试风暴；单次预测内同一组件最多调用一次。

### R9 - 赔率趋势隔离

赔率趋势仅分析竞彩官方SPF（odds_type=1X2，source_provider=SportteryOfficialWeb），不同玩法/供应商的赔率不混合。

### R10 - 可选组件不阻塞

天气、裁判等可选组件缺失时，不阻塞预测流程（missing_optional），仅记录在报告中。

### R11 - 验收结论互斥

验收脚本输出四种互斥结论：PRODUCTION_READY / SAFE_DEGRADED / EXTERNAL_BLOCKED / FAILED。

### R12 - 回退链保证

LLM生成失败时，先回退到Qwen备用模型，再失败回退到纯代码模板（无叙述）。回退不影响结构化数据的完整性。

### R13 - 数据准入必须先调研并由用户决定

所有候选数据和特征在进入正式概率、No Bet、风险、报告或离线校准前，必须完成专项调研并提交用户审核。未经用户明确决定，不得永久弃用、删除采集链路或宣称无预测价值。

### R14 - 权重和阈值必须可追溯

所有模型权重、风险阈值、价值阈值和数据新鲜度阈值必须记录来源、实验版本、适用赛事、评估指标和批准状态。临时经验值只能用于诊断基线并强制 No Bet。

### R15 - 穿测与返回协议不可绕过

每次生产验收必须执行全新库、历史库迁移、真实同步、缓存重复运行、对话叙述和故障注入场景，并输出统一机器可读证据。未完成任一必测场景时不得宣称生产就绪。

### R16 - 批次完成不可自证

分批修复时，每个批次必须先由 `scripts/finalize_batch.py` 自动生成 evidence，再由 `scripts/verify_batch_completion.py` 校验证据文件、审查记录、命令结果、外部复审策略、进度记录、独立提交和提交后工作区状态。`commit`、`changed_files`、`commands`、`coderabbit`、`external_review_required`、`progress_updated` 和 `independent_commit` 等关键字段不得手写；evidence 必须包含 `generated_by="scripts/finalize_batch.py"`。`blocking_gaps` 非空或脚本未通过时，不得进入下一批，也不得把该批次描述为已完成。

外部AI复审采用风险触发式硬门槛，不得作为所有小批次的无条件阻断项。凡修改生产预测链路、概率/权重/No Bet、数据库 schema/迁移、同步链路、安全/API/外部请求/密钥处理、开发验收脚本、Git hook、CI，或处于阶段收口、最终合并前，`external_review_required` 必须为 `true`，CodeRabbit 或等价外部复审必须成功且未处理问题为0。post-commit 验收器必须现场读取 `HEAD^..HEAD` 的实际提交改动判定高风险路径，不得只信 evidence 自报的 `changed_files`；发现高风险改动却写成 `external_review_required=false` 时必须失败关闭。仅修改文档、批次证据或测试补丁且不影响生产运行时和验收门禁的低风险批次，可以设置 `external_review_required=false`，但必须记录 CodeRabbit 尝试结果或未执行理由，并通过本地硬门禁。

高风险批次不得只用手写字段自证外部复审成功。`external_review_required=true` 时，evidence 必须提供 `coderabbit.artifact` 原始复审产物路径；`coderabbit.note`、`coderabbit.summary` 或 `coderabbit.raw_summary` 中出现无法运行、超时、失败、超过限制、未取得结论等语义时，即使 `ran=true`、`exit_code=0`、`unhandled_issues=0` 也必须失败关闭。evidence 的 `commit` 必须匹配当前 `HEAD` 或 post-commit 阶段的父提交，涉及代码、测试、脚本、CI、hook 或运行时依赖的改动必须列出 `required_artifacts`。普通修复批次不得使用 root commit 作为独立提交证明；post-commit 阶段工作区必须完全干净，`batch-N-evidence.json` 自身存在未提交改动也必须失败关闭。

批次门禁必须接入本地 Git hooks 和 CI。提交前运行 pre-commit 模式，推送前和CI运行 post-commit 模式。pre-commit 阶段的批次编号必须由 `--batch`、`FOOTBALL_ADVISOR_BATCH` 或包含 `batch-N` 的分支名明确给出；post-commit 阶段才允许使用包含 `批次N` 的提交信息兜底。无法确定批次编号时必须失败关闭。CI 必须拉取足够提交历史以读取 `HEAD^..HEAD`，不得用浅克隆造成普通提交被误判为 root commit；远端分支保护必须把批次门禁设为必需检查，禁止用本地 `--no-verify`、force push 或手写报告绕过最终验收。

批次关闭流程必须自动化固化，不能依赖执行者或其它 AI 手工记忆命令序列。批次关闭统一入口应负责生成 evidence、执行 pre-commit 门禁、创建独立提交、执行 post-commit 门禁并确认工作区干净；手工逐条运行命令只允许用于诊断失败原因，不得作为正式批次完成依据。统一入口未实现并通过自身门禁前，不得把任何批次标记为正式闭环完成。

验收角色只判断其它 AI 的原始交付是否达标时，必须使用只读接收审计，不得替对方生成 evidence、提交或关闭批次。只读接收审计至少校验工作区干净、普通批次不是 root commit、`verify_batch_completion.py --mode post-commit` 退出码为 0，并输出“达到/未达到”和阻断项。`scripts/audit_batch_acceptance.py` 是该场景的统一只读入口；`scripts/close_batch.py` 只允许执行者正式关闭自己的批次，不得由验收者用来补救其它 AI 的失败交付。
